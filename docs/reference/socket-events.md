# Події Socket.io

Основний канал зв'язку. Стан радіо роздається тільки тут — через REST його
отримати не можна.

## Підключення

```js
import { io } from 'socket.io-client';
const socket = io('http://localhost:3001', { withCredentials: true });
```

Походження клієнта має бути в `CLIENT_ORIGIN` на сервері, інакше з'єднання не
встановиться.

## Що приходить одразу

Ці події сервер надсилає сам, без запиту з боку клієнта:

- `sync` — повний стан радіо;
- `radio_hosts_mode` — чи ввімкнено режим живих ведучих;
- `usersUpdate` — активні слухачі;
- `radio_hosts_online` — лише коли режим ведучих увімкнено.

Щоб отримати `artToken`, клієнт має надіслати `listener_init` — див.
[Свій клієнт за 15 хвилин](/guide/quickstart-client#крок-3-отримати-arttoken).

## Колонка «Кому надсилається»

| Значення | Зміст |
|---|---|
| `усім` | широкомовно всім підключеним |
| `одному сокету` | адресно конкретному клієнту |
| `кімната …` | лише учасникам кімнати, напр. живим ведучим |

Події з кімнат ваш клієнт не отримає, поки не приєднається до відповідної
ролі — для звичайного слухача це нормально.

## Службові події

У переліку немає вбудованих подій Socket.io — `connect`, `disconnect`,
`connect_error` тощо. Вони працюють як завжди й описані в документації самої
Socket.io; протоколу цього радіо вони не стосуються.

З тієї ж причини відфільтровано `message` і `error`: у коді вони належать
UDP-сокету WebRTC-моніторингу, який теж названо `socket`, а не з'єднанню
Socket.io.

## Стан опису

Перелік генерується з коду, тож він завжди повний. Описи payload-ів
пишуться вручну — **зараз описано всі події**.

Щоб змінити опис, відредагуйте `reference/annotations/events.mjs` і
перезапустіть `npm run extract`. Якщо описати подію, якої в коді немає,
перевірка впаде — так ловляться перейменування.
